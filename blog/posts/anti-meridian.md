# 跨越 180° 经线：反子午线问题的来龙去脉

第一次把一条横跨太平洋的国界线画到 Web 地图上时，很多人会愣住：明明是一条连续的线，地图上却从最右边“断”到了最左边，中间横贯整个画面。

这不是 bug，是**反子午线（anti-meridian）**在作怪。

## 问题从哪来

Web 地图普遍用 **EPSG:3857** 投影，把地球展平成一张矩形图。经度范围被映射到 **-180° 到 180°**。可地球是个球，180° 和 -180° 本来是**同一条线**。

于是，一条连接 `[179, 0]` 和 `[-179, 0]` 的线段，按“字面坐标”画，就会横跨整个地图——从右画到左，而不是只跨 2° 的窄缝。

```
正常想要的：        ──●━━●──     (只跨 2°)
字面画出来的：  ●━━━━━━━━━━━━━●   (横跨整张图)
```

## 点、线、面，表现不同

- **点**：基本没影响，标在哪就在哪；
- **线/面**：最惨，会被拉成横贯屏幕的“长条”；
- 所以处理策略要分级。

## 常见解法：三副本平移

最朴素也最稳的办法，是把几何沿经度做三份副本：`[-360, 0, 360]`，让每段都落在连续区间里：

```js
function antiMeridianOffsets() {
  return [-360, 0, 360];
}

// 对一条线，分别画三份，总有一份是“连续”的
const offsets = antiMeridianOffsets();
offsets.forEach(dx => {
  const shifted = line.map(([lng, lat]) => [lng + dx, lat]);
  L.polyline(shifted).addTo(map);
});
```

线、面始终三副本；**点**如果数量巨大（比如上百万），只在 ≤1 万时才做副本，避免内存爆炸。

## 为什么不直接“裁剪”

理论上可以沿 180° 把几何切成两半分别绘制，但实现成本高、边界处理繁琐。对大多数 Web 场景，**三副本平移**已经足够，且几乎零成本。

> 我们项目里正是这么做的：线/面永远三副本，点超过一万才跳过。实测下来，跨太平洋的航线、洋中脊都能正确显示。

## 小结

反子午线不是数据错了，是“平面地图 + 球形地球”的必然妥协。理解它，下次看到地图被“扯开”，你就知道该往哪修了。
