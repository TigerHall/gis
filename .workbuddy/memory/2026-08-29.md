### 1. 3D 背景白底 + 跟随黑白模式

|---|---|---|

| `scene.globe.baseColor` | `#eceff1`（无影像处的底色） | `#1c1c28` |
| `scene.skyAtmosphere.show` | false | true |
| `scene.globe.showGroundAtmosphere` | false | true |
| `scene.fog.enabled` | false | true |
| `scene.sun.show` / `scene.moon.show` | false | true |

`assets/cesium-viewer.js` 新增 `applySceneTheme()`：从 `document.documentElement[data-theme]` 读取当前模式，
写入上面的属性。`scene.skyBox` 用 `show` setter（旧版本退化为 `= undefined`）；`_savedSkyBox` 缓存以便切回深色时还原。

### 2. 聚类数字不在中间 — 根因 + 修复

**根因**：Cesium `Label`（`EntityCluster` 在 `addCluster` 里 `cluster.label = entityCluster._clusterLabelCollection.add()`）
默认 `horizontalOrigin = LEFT`（值 1）、`verticalOrigin = BASELINE`（值 2）、`pixelOffset = (0,0)`。
我们只改字体/颜色/样式，没改原点 → 数字被画到锚点右上方。

**已用 Cesium 1.125 源码确认**（下载 `Cesium.js` + `@cesium/engine` 12.0.1 的 `EntityCluster.js`）：
- `LabelGraphics` 构造：`verticalOrigin = BASELINE`、`horizontalOrigin = LEFT`、`pixelOffset = ZERO`
- `addCluster` 只设 `show/text/id/position`，其余用默认 → 这就是数字偏移的根因

**修复**（`assets/cesium-geojson-adapter.js` clusterEvent 回调）：
```js
cluster.label.horizontalOrigin = Cs.HorizontalOrigin.CENTER;  // 0
cluster.label.verticalOrigin = Cs.VerticalOrigin.CENTER;      // 0
cluster.label.pixelOffset = new Cs.Cartesian2(0, 0);
```

同时 `ent.label`（要素标签）也补 `horizontalOrigin: Cs.HorizontalOrigin.CENTER`，
否则要素名也会被画到锚点右侧（之前只设了 `verticalOrigin: BOTTOM`，整体偏右半宽）。

**枚举值备忘**（已查 Cesium 1.125 源码）：
- `HorizontalOrigin = { CENTER: 0, LEFT: 1, RIGHT: -1 }`
- `VerticalOrigin = { CENTER: 0, BOTTOM: 1, BASELINE: 2, TOP: -1 }`

### 3. ⚙️ 设置后 3D 反应慢 — 两个改进叠加

**a) 旧 `updateOpacity` 是死代码**：判断 `if (pm.color)` — 但 `entity.polyline.material = Cs.Color.X`

旧代码因此透明度轻量路径等于没生效，**任何**色变都全量重建。

**b) 仅透明度变更走轻量路径**（`assets/geojsonloader.js` `reloadLayerWithNewMode`）：
变更前先捕获 `oldMode / oldColor / oldField / oldOpacity`，只有 `styleUnchanged && !forceRebuild && newOpacity !== oldOpacity`

## 第三轮迭代：3D 卡顿的根因 + 修复

用户反馈 3 个问题：
1. 图层渲染有延迟
2. Cesium 是 canvas 渲染？聚类是不是没必要？
3. 图层关了再开非常卡

### 根因调查（实测驱动，不靠猜）

写了 5 个 perf 探针（`assets/perf-3d.js ~ perf-3d5.js`），用 playwright-core + 系统 Chrome + SwiftShader 软件渲染做对照实验。

**关键发现**：`HeightReference.CLAMP_TO_GROUND` 是 3D 卡顿的唯一元凶。

实测帧耗时（n=1116 个 billboard）：
- 空场景基线：455ms/帧
- **billboard 贴地：5620ms/帧（12× 基线）** ⚠️
- billboard 不贴地：602ms/帧 ✅
- point 贴地：5635ms/帧
- point 不贴地：684ms/帧
- 仅线面（贴地）：703ms/帧 ✅（GPU 侧 GroundPrimitive，开销可忽略）
- 200 个 billboard 贴地：903ms/帧

**Cesium 在每帧的 BillboardVisualizer 里，对 heightReference≠NONE 的 billboard 做一次 `clampToHeight` 类的地形采样，CPU 侧 O(n)/帧。**

更反直觉的发现：当前地形实际是平坦椭球（Ion Token 空 → 走 ArcGIS Terrain 但 swiftshader 环境未生效），**`clampToHeightMostDetailed` 600 点耗时 58 秒（97ms/点）+ 前后高度差 = 0m** → 贴地付出了每帧 O(n) 采样的代价，**视觉收益却为零**。

Cesium 内部计时（adapter `loadGeoJson`）：
- GeoJsonDataSource.load 解析：9-15ms（n=1116）
- 我们的两遍后处理：18-22ms
- → **解析/后处理都不是瓶颈**，瓶颈在每帧的 visualizer

### 修复

**A. 点要素贴地策略解耦**（`assets/cesium-geojson-adapter.js`）：
- `heightReference` 与 `clampToGround` 解耦：线/面 `clampToGround` 保持 true（GPU 侧，几无开销，且不贴地的话长线会沿 3D 弦穿过地球），**点要素 `heightReference` 默认 `NONE`**
- 新增 `groundMode` 配置：`"none"`（默认）`"live"`（小图层显式启用，受 `POINT_GROUND_LIVE_MAX=300` 上限保护，超过自动降级并 console.warn）
- 热循环顺手优化：之前每要素 new 一次的 `Cs.JulianDate.now()` 改为复用变量
- geo-config 用法：`cesium: { groundMode: "live" }`

**B. 图层关→开 hide/show 复用**（`assets/cesium-viewer.js`）：
- 旧实现取消勾选 `viewer.dataSources.remove(ds, true)` 真销毁，重新勾选走完整 `GeoJsonDataSource.load` + 两遍后处理 → 大图层 30 秒+
- 新实现：
  - `hideLayer(id)`：仅 `ds.show=false` 挪到 `cesiumHiddenCache`（LRU 上限 `HIDDEN_CACHE_MAX=12`）
  - `addLayer(id, geoJson)`：先查 `cesiumHiddenCache`，命中瞬时 `ds.show=true`
  - `destroyLayer(id)`：真销毁，专供图层数据被删除（用户上传图层删除）
  - 旧 `removeLayer(id)` 保留接口语义 = hide
  - 隐藏中 `updateLayerOpacity` 也同步生效
  - `reloadLayer`/`reloadAllLayers` 必须用 `destroyLayer`（否则会命中隐藏缓存，样式变更不生效）
  - 暴露 `get layerStats()` = `{visible, hidden}`

**C. 大图层构建加载提示**（`assets/cesium-viewer.js`）：
- `addLayer` 真实构建时（要素数 ≥ 800）走 `runWithBusy` 显示忙碌卡片，文字带要素数
- 从隐藏缓存恢复的瞬时路径不显示

**D. 聚类参数调优**（`assets/cesium-geojson-adapter.js`）：
- `pixelRange` 45 → 28（避免全球视角下点被吞进少数大圈）
- `minimumClusterSize` 3 → 4
- 聚类气泡显式 `horizontalOrigin=CENTER` / `heightReference` 与点一致
- 「聚类圈不在地球表面的感觉」根因就是 CLAMP_TO_GROUND 每帧重算聚类中心位置 → 视觉抖动；改 NONE 后稳定在 height=0 椭球面（实测高度差 0m）

### 关于「Cesium 是 canvas？」

- Cesium 渲染后端是 **WebGL**（实测 `glVersion: "WebGL 2.0 (OpenGL ES 3.0 Chromium)"`，`renderer: "WebKit WebGL"`），`scene.canvas` 只是 WebGL 绘图表面
- billboard（点图标/聚类圈）是屏幕朝向的 2D sprite → 永远正面朝相机，不会随地球曲率变形（这是固有特性）
- 聚类**仍有必要**：① 上万点直接渲染会撑爆纹理图集 ② 全球视角下需要聚合才能看清分布密度 ③ 聚类气泡可点击展开

## 要素首次渲染慢 — 根因诊断（2026-08-29 晚）

用户提问：「要素渲染到图上会很慢，这是为什么？第二次倒是快点了」

### 结论
**慢的不是渲染，是取数 + 解压 + JSON.parse。第二次快 = IndexedDB 命中解析后的对象图。**

### 实测数据（CDP 限速 10 Mbps / 40ms RTT，pic.geojson.gz）

| 阶段 | 耗时 | 堆 |
|---|---|---|
| fetch 响应头 | 195ms | 60MB |
| **解压+JSON.parse** | **20,615ms** (89%) | 555MB |
| IDB 写入 | 1,368ms | **842MB** |
| IDB 读取（第二次） | **933ms** | 555MB |

第二次比首次快 **22 倍**。

### 数据体积（assets/geojson/ 共 70 图层 / 102MB gz）

| 图层 | gz | 解压后 | 预估首载 |
|---|---|---|---|
| PBDB | 26.0MB | **279.3MB** | 41.7s |
| pic | 24.4MB | **291.9MB** | 41.3s |
| states_provinces | 20.2MB | 60.8MB | 21.8s |
| Sedimentary_CGG | 9.7MB | 33.5MB | 11.5s |

**只有 4 个图层 >5s，其余 66 个都 <3.3s。**

### 关键结论
1. **瓶颈在 `Leaflet.GzIdbLoader.js:288` 的 `new Response(stream).json()`** —— 必须等流读完，
   再对完整字符串做 `JSON.parse`（279MB → 堆 555MB）。主线程集中开销。
2. **UI 其实没卡死**：20.6s 期间 longtask 累计只阻塞 2.5s（JSON.parse 尾巴 861ms + IDB 克隆 1367ms）。
   用户感知的"卡"主要是**20 秒零进度反馈**（只有一个静态小圆点 `title="加载中..."`）。
3. **内存风险比慢更严重**：单大图层堆峰值 842MB，PBDB + pic 同时勾选很可能 OOM。

### 小图层基线（本地无限速）
plate16 47ms / volcanos 148ms / ODP 183ms；关→开（内存 layerCache 命中）**7-9ms**。
开销分布：`addTo(map)` 60-70%（3 个世界副本 → 1293 点变 3879 marker），`L.geoJSON` 20-25%，取数 <1%。

### 优化方案（待用户选）
- **A 加载进度提示**（中工作量/低风险）— `fetchGz` 用 ReadableStream 读 Content-Length 上报百分比
- **B Web Worker 转移解压+parse**（中/中）— 主线程零阻塞，但 279MB 对象图回传仍 ~1-2s
- **C 数据瘦身**（大工作量/低风险，治本）— 4 个巨无霸按 zoom 分级或地理分块，40s → 1-2s
- **D 大图层二次确认**（小/极低）— 管理预期
建议：先 A+D，再 C。

## 要素渲染慢 — 方案 A 实施 + IDB 缓存修复（2026-08-29 晚，续）

用户选定 **A 加载进度提示**，并追问"2D 图层为什么没那么慢，应该调用 idb 的数据，挺快的才对"。

### 实施内容

1. **进度条链路**（`Leaflet.GzIdbLoader.js`）
   - `fetchGz(url, onProgress)`：在 `DecompressionStream` 前插计数 `TransformStream`，按 gz 字节上报百分比（100ms 节流）
   - **`parse` 阶段必须放在 TransformStream 的 `flush()` 里** —— 放在 `.json()` 之后会在下载刚开始时就误报"解析中"（踩过的坑）
   - `fetchWithCache` 命中缓存后加 **`nextPaint()`**（双 rAF + setTimeout）：先让浏览器把"读缓存"标签画出来，再跑 279MB 反序列化。不加这一步标签根本来不及绘制

2. **IDB 缓存可靠性（用户追问挖出的真 bug）**
   - **根因**：`fetchWithCache` 里 `setCache(url, data)` 是 **fire-and-forget**。大图层写入 1-2s，用户在此之前刷新 → 缓存丢失
   - 实测：配额 10GB 充足；等 25s 能写入；但**"加载完立即刷新"缓存必丢**
   - 修复：`await setCache(...)` 后再 resolve。复测"立即刷新后缓存仍在 ✅"
   - **这解释了大图层首次 40s / 二次 1.2s 的 22× 差距为何用户只觉得"快点了"**

3. **`updateLayerProgress()`**（`geojsonloader.js:1247`）
   - 懒建 `.layer-item-progress` + `.layer-progress-text`，阶段：读缓存/下载N%/解析中/写缓存/渲染中/完成
   - **发现的 bug**：`p === null` 清理分支只调了 `bar.removeAttribute("data-indeterminate")`，**从未真正摘除节点** → 每个加载过的图层永久残留一个 2px 空进度条（不可见但带着上次宽度）。已改为 `parentNode.removeChild(bar)`

4. **对比度（WCAG AA）**
   - 进度文字原用 `var(--accent)`(#99cc99)，浅底 #fafafa 上实测 **1.76:1**（AA 要求 4.5:1）
   - 新增小字专用 `--c-green-text-strong`（浅 `#3d7a3d` / 深 `#88cc88`）→ 实测 **4.97:1 ✅**，双主题 6 种底色组合 4.76~9.93:1 全过

### 实测结果（playwright-core + Chrome，6Mbps/40ms 限速）
下载百分比与填充一致（209 采样，偏差<1%）✅ ｜ 不确定阶段 33%+扫动动画 ✅ ｜
不撑高行（32→32px）✅ ｜ 文字 10px/15px 不溢出 ✅ ｜ 完成后清理+开关 6 次无泄漏 ✅ ｜
刷新后命中 IDB 显示"读缓存"@21ms ✅ ｜ `ERRORS: none`

### 探针踩坑（复用价值高）
- **`page.evaluate` 传字符串函数会被当表达式求值 → 返回 `undefined`**。必须传真实函数
- **等待"加载完成"的判定必须先看到进度条出现过**：`click()` 到首个进度事件之间有窗口，只判断"无进度条 && checked"会立刻误判完成（实测耗时 0.0s）

- Playwright 每次启动是全新 profile → **IDB 每次都是空的**，首次加载天然是冷加载，测试可确定性复现
- 采样去重键要加粗粒度（如 `Math.round(width/2)`），否则 width transition 每帧一条样本全是噪声

## 3D 白色蒙层 + 地球瓦片预算调优（2026-08-29 夜）

用户反馈：①「黑色背景下的地球是不是加了白色蒙层，很模糊」②「3D 比 2D 慢很多，倒排索引都好了 3D 才出来；
最后一个图层只有 1 个面，也等了很久才进入地球」。

### 根因（推翻了上一轮"数据解压慢"的假设）

**慢的不是渲染。** 实测分段（1280×800，外网直连）：

| 阶段 | 耗时 |
|---|---|
| Cesium 引擎下载（CDN 4MB） | 1.7~8.4s |
| **Cesium 引擎解析+执行** | **4.75s**（V8 编译，纯 CPU） |
| initViewer + 地形 | 0.13s |
| 地球底图瓦片（优化前） | 24.2s |
| **5 个 GeoJSON 图层 3D 构建** | **0.30s**（占全程 1%） |

各图层构建：DupalOcean(1面) 9.5ms / ChinaCounty(2089) 55ms / 海区(306) 33.5ms / 地名点(5555) 169ms / 港口(1081) 33ms。
**2D 数据+倒排索引 1.9s 全好** → 用户等的是引擎 8s + 地球 24s，与 GeoJSON 数据量无关，所以"1 个面也慢"正常。

### 修复 1：大气三件套（白色蒙层）

深色 `THEME_DARK` 原 `skyAtmosphere/groundAtmosphere/fog` 全开。
- `showGroundAtmosphere` = 叠在**地表影像之上**的大气散射 → **发白发糊主因**
- `scene.fog` = 远处雾化
- `skyAtmosphere` = 地球**外缘**光晕（轮廓外，不覆盖地表）

深色主题三者改 false。新增 `CesiumViewer.setAtmosphere(true|false|null)` 运行时开关（null=跟随主题）。

### 修复 2：globe.maximumScreenSpaceError（关键杠杆）

SSE 越小 → 瓦片请求**指数增长**。原用 Cesium 默认 2。

| SSE | 瓦片请求 | tilesLoaded | 天地图429 |
|---|---|---|---|
| 2（原默认） | **566** | 24.2s | 11~19 |
| 24(首屏)→**12**(稳定) | **35** | **10.0s** | **0** |

天地图密集请求会 429 限流 →「请求越多→限流→重试→更慢」死循环，压住瓦片数本身即提速。

实现 `setupGlobeTileBudget()`：首屏 SSE_FAST=24；`globe.tileLoadProgressEvent` 排队数归零后降 SSE_FINE=12（只降一次）。

**⚠️ 稳定档不能 < 12**（实测首屏均为 24）：SSE=12→35瓦片/10.2s ｜ SSE=8→168/15.3s ｜ SSE=4→235/16.9s 且 tilesLoaded 反复回退 30 次。
最初取 4 就是这个坑——降级触发新一轮大规模加载，120s 都稳不下来。

### 探针踩坑（复用价值高）
- **不要劫持 `script.src` 的 setter** 做埋点（`Object.defineProperty` 覆盖会破坏原生加载行为，脚本永不加载，实测卡 95s）
- **`primitive.ready` 语义不可靠**：Cesium 内部对象（`Ef`/`Cr` 等压缩名）8s 仍 false，不能作为"是否显示"判据。用 `globe.tilesLoaded` 或截图像素
- **截图像素法要先等基线稳定**：底图没加载时画面全黑（均值 0），会把"地球出现"误判成"图层出现"
- 我这边 ArcGIS 地形/底图部分不可达会降级，`terrainProvider` 要用 `instanceof Cs.EllipsoidTerrainProvider` 判定，不能只看构造名（压缩后是 `GV`/`Fy`）
- `CesiumViewer` 取 viewer 用 **`.viewer` getter**，没有 `getViewer()` 方法
- 无 pngjs 时：Playwright 截图 → base64 → 页内 `Image`+`canvas` 解码统计像素，比 node 端手写 PNG 解码省事

## 3D 引擎空闲预加载 + 下载进度条修复（承接上一轮）

### 1. 进度条 8 秒不动的根因（重要，易复现）
CDN 返回 `content-encoding: gzip` + Chunked，**`content-length` 缺失**（实测 `(none)`）。
`fetchWithProgress()` 里 `total` 为 0 就走 `res.text()` 回退分支 → 整个下载期 0 次回调，
只在结束瞬间报一次 `onProgress(1)`。用户看到的就是「卡了 8 秒然后跳 100%」。

**修法**：
- 不因缺 `Content-Length` 放弃流式读取，分母回退到实测常量 `CESIUM_JS_BYTES = 5140708`（v1.125 解压后真实体积 ≈4.9MB，定义在 `CESIUM_VERSION` 旁，升级时同步改）
- 百分比封顶 98%，100% 留到 `r.done`，避免「条满还在转」
- 新增 `phase` 参数（`"download"` / `"parse"`）：4MB 脚本解析会独占主线程 3~5s，
  执行前先 `report(1,null,"parse")` + `nextPaint()` 让「正在解析 3D 引擎（首次较慢）…」真的画出来

改后实测：2%→98% 平滑递增（6.0s）→100%→解析→初始化，总计 6.6s。

### 2. 空闲预加载（只对用过 3D 的用户）
- `localStorage` `dupal_3d_ever_used`，首次激活成功时 `mark3dUsed()` 写入 → 新用户首屏零开销
- `load` 后 4s → `requestIdleCallback(timeout 20s)` → `preloadCesium()`
- 守卫：`saveData` / `effectiveType` 为 2g|slow-2g 不预加载
- **只下载+解析 JS，不建 Viewer、不切视图**，不违反「不要自动进入 3D」
- **加载订阅者模式**（关键）：`_loadSubs` + `broadcastLoadProgress` + `settleLoadSubs`；
  `activate()` 只挡 `isActive` 不再挡 `isLoading`，后台预加载中用户点击可「搭车」共享进度，
  不被吞掉（实测遮罩正常显示 2%→93%→解析→初始化）
- 预加载失败不影响手动激活（abort 首次请求后手动点击仍成功）

验证 4/4 通过：① 新用户 Cesium 请求 0 次 ② 老用户预加载后点开 **183ms** 且未自动进 3D
③ 预加载中点击显示完整进度 ④ 预加载失败仍可手动激活。
上一轮地球瓦片回归复测仍全绿（大气全关 / SSE 24→12 / 35 瓦片 / 429 归零 / 0 回退）。

### 探针经验（复用）
- **`page.evaluate` 轮询会被 4MB 脚本的同步解析阻塞**，采不到中间态 →
  改用**页内 MutationObserver** 记录遮罩 DOM 变更，主线程的变更一定被记录
- 判「是否有 Content-Length」用 `page.on("response")` 读 `r.headers()`

## 瓦片清晰度：八子域 + SSE=2 翻案（2026-08-29 夜）

### 用户反馈
"地图瓦片似乎有点太糊了……瓦片加载的程度可以用和 Leaflet 设置的 maxNative 一样即可。
现在的问题是看起来放大后还是最低级的瓦片层级。"

### 根因（不是 SSE）
上轮为了压 429 用了 `SSE=24→12` 渐进。**真因是只用了 t0 单子域**——Cesium 的
`RequestScheduler` per-server 并发上限默认 6，单域全挤一台 → 429 → 重试 → 死循环，
只能降 SSE 换清晰度。

### A/B 决定性数据
| 方案 | 全球就绪 | zoom8 稳定 | 瓦片 | 429 | 锐度 | 子域 |
|---|---|---|---|---|---|---|
| A 原 SSE=24→12 + t0 | 超时 | 12.6s | 184 | 0 | **1.4** | 单域 |
| B SSE=2 + t0 | 34.4s | 15.1s | 392 | 0 | 94.6 | 单域 |
| **C SSE=2 + t0~t7** | **6.8s** | **3.8s** | 392 | 45 | **568.5** | **8 子域** |
| D SSE=2 + 限流(per-server=3) | 33.6s | 14.1s | 392 | 0 | 94.6 | 单域 |

**C 比 A 又快又清**：锐度 1.4 → 568.5（**407×**），时间 12.6s → 3.8s（zoom8）。
D 限流无效。11.5% 429 触发但 Cesium 内置重试扛住。

### 修法
- 提取 `TDT_SUBDOMAINS = ["0"…"7"]` + `createTdtProvider(svc, tk)` 工厂
- 三个底图（img_w/vec_w/ter_w）+ 四个覆盖层（ibo_w/cva_w/cia_w/cta_w）全用八子域
- 删 `setupGlobeTileBudget` 渐进逻辑，直接 `SSE=2`

### 第二个问题：「瓦片加载会不会影响 JSON 图层渲染？」
**不会**。GeoJSON 走 `DataSource → Entity → Visualizer` 管线，与瓦片请求独立。
瓦片慢时 entity 仍先出现，视觉上"浮在黑背景"。实测 5 图层 3D 构建 0.30s，
瓦片 24s 时 entity 早已显示。

### 第三个问题：预加载
按用户说"本身我这个就做了 PWA，引用的 js 应该会记录在浏览器本地的"——
`service-worker.js` 动态缓存同源资源，首次开 3D 后 Cesium.js 已落到 Cache Storage，
第二次直接秒开。空闲预加载边际收益小，**移除自动调度**。
保留 `CesiumViewer.preloadNow()` 手动入口与 `_loadSubs` 并发安全基础设施。

## Cesium 原生控件评估 + 部分启用（2026-08-29 深夜）

用户想用「缩放控件」开关兼职控制 Cesium 控件组，评估结论：
- **baseLayerPicker 不平替**：只能单选底图，无法表达 OGV 的多选覆盖层/业务图层；且引入 3D→2D 反向状态同步竞态，2D 唯一状态源架构更干净（保持现状）
- **sceneModePicker 开启**（用户主动要看 3D/2D/哥伦布效果）：构造参数 `sceneModePicker: true` 常驻
- **fullscreenButton + navigationHelpButton 启用**，走方案 A：构造 true + CSS class 控制，zoomToggle 兼职开关

### 改动（3 文件 + SW）
- `assets/cesium-viewer.js:1324-1343` — 构造参数 `sceneModePicker: true, navigationHelpButton: true, fullscreenButton: true`（其余控件保持 false；Cesium 控件是构造时一次性创建，事后无法 options 增删）
- `assets/cesium-container.css` — `body:not(.ogv-zoom-ctl)` 下隐藏 `.cesium-fullscreenContainer` / `.cesium-navigationHelpButton-wrapper` / `.cesium-navigation-help`（帮助面板也藏，防误开漂浮）
- `assets/app.js` — zoomToggle 从 `control:` 映射改为 enable/disable 钩子（enable 优先于 control 执行）：`map.zoomControl.addTo(map)` + body 加 `ogv-zoom-ctl`；desc 补「3D 模式下同步显示全屏与操作帮助按钮」
- `service-worker.js` — CACHE_NAME v2.3.3 → v2.3.4

### 关键事实
- initToggle 中 `cfg.enable/disable` 优先于 `cfg.control`（app.js:1464-1480），所以 zoomToggle 要兼职工必须先给 enable/disable
- CSS class 方案免疫 viewer 懒初始化时序：body class 与 viewer 生命周期解耦
- 已知坑：sceneModePicker 的 Cesium 2D 与 Leaflet 2D 是「两个 2D」，业务代码（相机同步/拾取）未适配非 3D 模式，仅看效果用

### 收尾（同日）：sceneModePicker 纳入缩放控件开关 + 移除全屏按钮
- `cesium-viewer.js`：`fullscreenButton: false`（去掉，用处不大）；`sceneModePicker` 保留 true 但不再常驻，显隐改由 `ogv-zoom-ctl` 控制

- `service-worker.js`：v2.3.4 → v2.3.5
- 结论：3D 辅助控件（三视图 + 帮助）统一由 zoomToggle 控制，默认（zoomToggle 关）全隐藏
