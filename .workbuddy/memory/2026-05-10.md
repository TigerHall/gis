## 修复 addUserLayer 内存爆炸问题

### 根因
`geojsonloader.js` 中 `addUserLayer` 函数（第1366行）为了计算 `fitBounds`，创建了完整的 `L.geoJSON` 对象，其内部会为每个点生成 Marker DOM 对象，45万点即 45万个 Marker，且缓存在 `layerBoundsCache[uid]` 永不释放，导致内存爆炸。

### 修复内容
1. **删除 `L.geoJSON` bounds 计算**：移除了原来的 `var baseGeoJson = L.geoJSON(...)` 和 `layerBoundsCache[uid] = baseGeoJson`
2. **改为纯坐标数组遍历**：直接从 `fixedData.features` 遍历坐标求 minLat/maxLat/minLng/maxLng，零 DOM 对象创建
3. **保留 flyToLayer 功能**：计算出 `L.latLngBounds` 后，存一个轻量包装 `{ getBounds: function() { return b; } }` 到 `layerBoundsCache[uid]`，供 flyToLayer 调用
4. **清理无效 removeLayer 调用**：`unselectAllLayers` 中删除了对 `layerBoundsCache` 的 `map.removeLayer` 调用（该对象从未 addTo 地图）

### 文件
- 修改：`assets/geojsonloader.js`

### 技术细节
- 问题与文件名无关，是原有代码 bug（换名之前就已存在）
- 支持 Point/MultiPoint/LineString/MultiLineString/Polygon/MultiPolygon 等所有几何类型的 bounds 计算
- 内置图层（按钮图层）路径的 `layerBoundsCache` 存的仍是 `L.geoJSON` 对象，不受影响

## 修复一加载就爆内存问题（本次会话）

### 根因分析
用户反馈：45万点 GeoJSON 一加载就爆内存，不是渲染问题，是解析大体积 JSON 的问题。

**IndexedDB 存储位置**：数据存在硬盘上，但从 IDB 读取时整个对象会被完整反序列化到内存。45万点完整加载到内存是爆内存的直接原因。

### 修复内容

#### 1. `assets/Leaflet.GzIdbLoader.js`
- **去掉 `size: JSON.stringify(data).length`**：`setCache` 中原本用 `JSON.stringify(data)` 完整序列化来计算大小，产生巨大字符串副本，随后 `store.put(record)` 又会再序列化一次存入 IDB。改为不再存储 `size` 字段，彻底避免这次序列化。
- **`getCacheSize()` 适配**：旧缓存记录有 `size` 字段，新缓存没有。改为只累加有 `size` 字段的记录，不再对无 `size` 的记录做 `JSON.stringify` 回退（避免再次炸内存）。

#### 2. `assets/geo-utils.js`
- **新增 `computeBounds()` 函数**：直接根据 GeoJSON 坐标计算 `L.LatLngBounds`，不构建 `L.geoJSON` Layer，避免大数据内存爆炸。已加入 `window.GeoUtils` 导出。
- **修复 `shiftGeoJSON(offset=0)`**：原实现 `JSON.parse(JSON.stringify(geojsonData))` 会完整深拷贝。`offset=0` 时直接返回原对象，不再拷贝。
- **修复 `fixAntimeridian()`**：原实现同样 `JSON.parse(JSON.stringify(geojsonData))` 深拷贝。改为直接在 `geojsonData` 上修正（来自 IDB 缓存的副本，修改不影响 IDB 存储），不再拷贝。

#### 3. `assets/geojsonloader.js`
- **`searchRegistry` 不持有完整 features**：`>10000` 点的数据集，`features` 字段存 `null`，只保留 `featureCount` 信息。小数据集不受影响。
- **`layerBoundsCache` 改用 `computeBounds()`**：原来用完整 `fixedData` 构建 `L.geoJSON` Layer 来计算 bounds，构建完后该 Layer 永久驻留内存。改为调用 `computeBounds()` 直接计算 bounds 对象（轻量 `L.LatLngBounds`），内存大幅降低。
- **`onFeatureClick` 仅小数据集设置**：45万点 Canvas 层的点击回调原本通过闭包持有 `shifted.features`（完整 45万点），永久无法释放。改为 `>10000` 点时不设置 `onFeatureClick`（点太密，点击弹出也不实用）。
- **`loadGeoJSONLayer` 适配**：`layerBoundsCache` 现在存的是 `L.LatLngBounds` 对象，不再有 `.getBounds()` 方法，已修复调用方式。
- **`flyToLayer` 适配**：同时兼容 `L.LatLngBounds`（新格式）和 Layer 对象（旧逻辑）。

### 修复效果（估算）
- 45万点完整 GeoJSON：~200MB
- 修复后 Canvas 层 `_features` 只存 `{lat, lng, color, _idx}`：约 22.5MB
- 消除了 `JSON.stringify(data)` 双重序列化、`shiftGeoJSON` 深拷贝、`fixAntimeridian` 深拷贝三处巨大内存分配
- `fixedData` 在 `loadGeoJSONLayer` 的 `.then()` 回调结束后可被 GC 回收

## 聚类全缩放级别启用 + Canvas 图层复用优化

### 问题1：聚类只在 zoom ≤ 13 时出现
- **根因**：`Leaflet.MarkersCanvas.js` 第252-255行，`useCluster` 判断条件包含 `zoom <= this.options.clusterMaxZoom`（默认14），导致高缩放级别聚类消失，大量点直接渲染导致卡顿。
- **修复**：移除缩放条件，聚类在所有缩放级别都启用（当 `clustering: true` 且可见点数 ≤ 50000 时）。
- **修改文件**：`assets/Leaflet.MarkersCanvas.js`（第252-255行）

### 问题2：Canvas 渲染图层颜色模式切换导致重复卡顿
- **根因**：`reloadLayerWithNewMode` 函数在颜色模式切换时会清除缓存并完全重建 Canvas 图层，导致用户操作时重复卡顿。
- **修复**：检测是否为 Canvas 渲染的图层，如果是则直接复用已加载的图层，通过 IndexedDB 缓存获取 GeoJSON 数据并更新，避免清除缓存和重建。
- **修改文件**：`assets/geojsonloader.js`（`reloadLayerWithNewMode` 函数）

### 文件
- 修改：`assets/Leaflet.MarkersCanvas.js`
- 修改：`assets/geojsonloader.js`

### 技术细节
- 聚类全缩放级别启用：高缩放级别下可见点数 ≤ 50000 时仍会聚类，超过则直接 Canvas 渲染。
- Canvas 图层复用：`L.GzIdbLoader.fetch` 已缓存解压后的 JSON 在 IndexedDB 中，重新获取时无需解压，速度很快。
