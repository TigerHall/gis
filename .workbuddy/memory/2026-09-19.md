### 为什么 Leaflet 便宜（关键机制）
Leaflet 所有矢量渲染都走 `map.latLngToLayerPoint()` → `crs.latLngToPoint()`。装 proj4leaflet 后：
- GeoJSON 几何、`L.Circle`、`markerClusterGroup`、divIcon 标记 → 自动重投影，**数据零改写**。
- `measure-tools.js:157` 用 `L.LatLng.distanceTo()`（球面 haversine）→ **与 CRS 无关**，测量读数不用动。
- `basemap-manager.js:133` 的 `wms` kind 走 `L.tileLayer.wms`，其 `crs` 默认取 `map.options.crs.code` → **换 CRS 后 WMS 自动改发 `SRS=EPSG:3413`**，引擎一行不用改（只需让配置能声明 crs）。

### 必须改造的 5 个断点
1. **全部底图失效**：天地图/ArcGIS/Esri Wayback/高德/本地 XYZ/GEBCO 全球 WMS/ETOPO 整幅 jpg 全是 Mercator 或经纬度产物，极地下一张不能用。
2. **跨 180° 三副本**（`geojsonloader.js` `buildGeoJsonLayerGroup`，调用点 `1624/2168/3836/3850`）= Web Mercator 世界环绕的产物 → 非 Mercator CRS 下必须按 CRS 关闭，否则每条线画 3 遍。
3. **map 实例引用**：`basemap-manager.js:21`、`feature-panel.js:11` 是**加载期快照** `var map = window.map`；`geojsonloader.js` 用模块级 `map` 变量（`addTo(map)` 14 处）。Leaflet **不支持运行时改 `map.options.crs`** → 换投影须销毁重建 map，这几处必须改惰性读取，否则断言旧实例。
4. **`cesium-viewer.js:415/423` `zoomToHeight`/`heightToZoom` 含 `Math.cos(lat)`**：lat→±90 时 height→0、`log2(0/…)`→-Infinity，**极地必崩**；且 Mercator 下本应是 `1/cos(lat)`，此式本身就有偏差。应改用 `map.getScale()`。
5. **`Leaflet.Graticule.js`** 经纬网在极地下变放射状，须换极坐标网或隐藏。

### 三副本研判（用户痛点第 1 项）
**根因**：把「世界副本」当**数据概念**（`shiftGeoJSON` 深拷贝整份数据、平移 ±360°），而不是**渲染概念**（渲染时的整数偏移）。

**现状代价**：① 线/面数据内存 ×3；② 几何对象 ×3、渲染开销 ×3；③ 副本要素在搜索/图例/属性表可能重复计数，`_featureIndex` 要手动重映射（`geojsonloader.js:891-895` 那段补丁就是痕迹）；④ 点图层用 `totalPoints <= 3000` 作阈值（`geojsonloader.js:877-880`）→ >3000 点只有单副本 → 平移过去就「点消失」。

**既有但未接线的资产**：`geo-utils.js:337` `fixRingCoords`（经度**展开**，消除相邻点 >180° 跳变）、`fixGeometryCoords`、`fixAntimeridian`（就地修正、不深拷贝）。三者**从未被业务代码调用**（`fixAntimeridian` 连导出都没有）——上次尝试过的优雅方案留在了库里当死代码。

**推荐方案：把世界偏移从数据层下移到渲染层**
- 数据永远只 1 份真实经纬度；副本 = 渲染时整数 `k·360°`。
- Canvas 点层（`Leaflet.MarkersCanvas.js:281/289/316`）：`_redraw` 内算 `worldOffset`，视口查询 bbox 减去它、绘制坐标加上它 → **13 万点全量环绕、内存零增长**，`totalPoints<=3000` 阈值可删。
- SVG 矢量层：数据侧用 `fixAntimeridian` 展开（相邻顶点经度差 <180），渲染侧**整条几何统一偏移**（按几何锚点相对地图中心定 `k`）——必须整体偏移，逐顶点吸附会把跨 180° 的线撕成横穿全球。

### 坑一：`tileLayer.options.bounds`（经纬度包络）→ 一块瓦片都不出
- 根因：**极点在正方形内部，不在四条边上**。只采样四边 → 得到纬度 38.8°~52.6° 的环带；
  视口里靠近极点的瓦片纬度 60°~90° → 不相交 → `_isValidTile()` 末尾 `overlaps()` 全 false。
- 实测对照（同 URL 同视口）：带 bounds 时 `_isValidTile(2,2,2)=false`、DOM 瓦片 **0**；
  去掉后 `true`、瓦片 **8 张全加载**。
- 而且这个 bounds 本就多余：CRS 给了 `bounds` → `crs.infinite=false` → Leaflet 用
  `getPixelWorldBounds()` 推出 `_globalTileRange`，极地 CRS 无 `wrapLng/wrapLat` → 越界 x/y 已被拒。
  实测 `globalTileRange=(0,0)-(7,7)` 正好 = GIBS level 2 的 8×8。→ **删掉 `modeEnvelope()`**。

### 坑二：极地下 `map.getBounds()` 退化成零高度纬度线 → 点要素全被裁
- 极点居中 → **视口四角到极点距离完全相等** → Leaflet `getBounds()` 只取两个对角点 →
  latMin == latMax → 高度 0 的环带。`MarkerClusterGroup._getExpandedVisibleBounds`、
  `MarkersCanvas` 的 RBush 视口查询、大图层视口过滤**全部整批丢要素**；
  它调的是 `.pad(1)`（按比例放大），对 0 高度毫无作用，没法靠 pad 兜。
- 修在**地图实例层**（`patchBounds()`）：沿视口矩形 5×5 网格在**像素空间**采样取真实极值；
  极点落在视口内时纬度取 ±90、经度显式写 -180~180（绕满一圈 LatLngBounds 表达不了「整圈」）。
  一处修好，下游全部自动正确。
- 不变量验证（全球 2°×5° 网格 6408 点）：四场景**漏 = 0**（这条必须成立）；
  「多」= 极冠用经纬度盒子表示的固有外接误差，只损失一点裁剪精度，不丢数据。

### 坑三：`resolutions` 6 项 vs `maxZoom: 6` → z6 抛 "Attempted to load an infinite number of tiles"
- proj4leaflet `scale(z)` 就是 `_scales[z]`；表里没有的层级 = `undefined` → Leaflet
  `getZoomScale()` 拿它做除法得 NaN → `_pxBoundsToTileRange()` 非有限 → 抛异常。
- `zoomSnap: 0` 会插值到 `_scales[z+1]` → 不是「最大那级不能用」，而是**滑到 z5.5 就崩**。
- 两处一起修：`resolutions` 补到 7 项；引擎加 `maxZoomFor(mode)` 取 min 并告警兜底。

### 顺带修：GEBCO 预烘影像其实一直是坏的
- `putImageData` **不改变画布尺寸、也不缩放**，是 1:1 覆盖写 → 1024×1024 的结果只有前 222 行

### ② 极区板块填充整块消失 —— 根因是 `fixAntimeridian` 展开极冠环
**症状**：全球面图层（大陆/大洋板块）在北极具顶出现横贯全宽的纯色平板带、南极冠无填充。

**诊断链（走过的弯路要记住）**：
1. 先怀疑 Leaflet `_clipPoints`（开折线 run + `Z` 各自闭合）。→ **错**。
   `noClip:true` A/B 只改了北极几何，南极没变。
2. 又怀疑 `probe-chords` 找到的「长水平弦」。→ **测量工具本身有 bug**：
   把 `d` 字符串正则取点后各子路径被说平成一串，会跨子路径产生假弦；
   且把「屏幕 y 恒定」误当成「源数据纬度恒定」。**原始数据里 0 条长水平段**。
3. 用 `probe-hit-antarc` 的 `_containsPoint` 判「有没有面覆盖」。→ **错**：
   Leaflet `Polyline._containsPoint` 是**到边的距离**判定，不是填充判定。
4. 正解：`path.isPointInFill(point)` + `svg.getScreenCTM().inverse()` 换算用户坐标；
   再离线用非零环绕复算对照 —— 两边**一致**，说明是几何本身，不是渲染管线。
5. 最后用**单环最小页面 A/B**（`ring-ab.js`）一次定死。

**根因**：极冠环是「沿 ±180° 切开、靠极点段闭合」的写法
（`(-179.999,-89.999) → (-110,-89.999) → (179.999,-89.999)`）；Mercator 把 |lat|>85.051
钳到 ±85.051，那段**正好躺在地图上下边**上横贯一圈，环就着地图边闭合。
`fixRingCoords` 的展开把 `-110 → 179.999`（290°）折算成 -70° → 极点段折叠成零面积尖刺
→ 环改走一条**横贯地图的弦**闭合 → 非零环绕自我抵消 → 极冠整块没了。

**修法**：`fixRingCoords` 开头，含 `|lat| ≥ 87` 顶点的环**原样返回**（`POLAR_RING_LAT = 87`，
取在真极冠与格陵兰最北 83.6° 之间）。极冠环本来就已在 ±180° 切开，无跳变可展开。

**单环 A/B（南极冠 913 点环，6 采样点）**：
原样 **6/6**（北极 3/6）｜展开 1/6（1/6）｜极点吸附 1/6｜展开+矩形裁剪 1/6。
→ 后三种候选全否掉，只有「不展开」是对的。

### 关键教训（工具层）
- **探针也会说谎**：`d` 属性跨子路径说平、`_containsPoint` 是边距不是填充、
  `getScreenCTM()` 在平移后过期（必须每次采样前重取 —— 我用过期 CTM 得出
  「世界副本平移后覆盖为 0」的假结论，靠截图才纠正）。
- 判定「面是否覆盖某点」只有两个可信办法：`path.isPointInFill()`（浏览器）
  与离线非零环绕复算；两者一致才说明是几何问题。
